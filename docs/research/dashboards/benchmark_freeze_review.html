论文口径

最稳妥的写法是：主 90 衡量 authoring 能力；external 66 衡量跨公开协议、公开文档和 backend-neutral 场景的泛化能力；runtime20 衡量真实机器或 shadow recovery loop 的安全恢复能力。

避免写成“全部 66 道来自真实外部数据集”。正确表述是“36 public protocol adaptations + 13 doc-derived PyLabRobot tasks + 17 project-authored backend stress tasks”。

runtime20 真机/恢复 loop benchmark

范围类别case通用性用途
R001-R004consumablesmissing tip、tip budget、partial pickup/drop failure、waste route unavailable。高验证 loop 是否能在耗材状态不安全时阻止继续执行。
R005-R009deck/labwareoccupied slot、wrong labware、missing labware、state-source conflict、offset/position unknown。高到中验证 deck state reconciliation、collision avoidance、preflight block。
R010-R014liquid stateno liquid、insufficient source volume、clog/bubble、liquid class mismatch、partial transfer contamination。高验证液体状态、死体积、污染风险和异常移液后的恢复策略。
R015-R018module/gripperthermocycler lid、heater-shaker latch/shaking、module thermal error、gripper preconditions。中验证有模块和 plate mover 的工作站是否能正确阻止危险动作。
R019-R020control stateinterrupted run/home state unknown、human intervention before resume。高验证真实 run loop 的 pause、resume、human confirmation 和安全恢复边界。

这些不是 authoring task，而是 runtime recovery cases。大部分逻辑对 Opentrons Flex/OT-2、Hamilton、Tecan、Beckman 等移液工作站都有意义，但具体传感器和自动恢复能力依赖硬件；没有对应硬件时应记录 not_run_hardware_unavailable，不要换题。

真实机器怎么测 run loop

  • 先跑 shadow/offline：用 scenario_benchmark.py 或 recovery_shadow_benchmark.py 验证 detection、block、safe escalation。
  • 再做 dry-run/preflight：加载真实 deck state，但不允许危险 motion；确认 robot state、labware、tip/liquid inventory 都被采集。
  • 最后选少量低风险真机 case：例如 R001、R005、R006、R010、R019、R020，逐步打开实际动作。
  • 每次真机运行必须保存 summary、robot logs、截图或视频、human intervention count、recovery time。

核心 loop 开发缺口

  • runner 需要把 recovery event、gatekeeper decision、robot state snapshot 写成统一 trace。
  • 需要显式 autonomy mode：gated、assistive、auto-safe-only，默认仍应是 gated。
  • MCP recovery adapter 可以作为可选薄层接入，但不要在 benchmark 清理前强依赖。
  • 真机执行前需要 case-to-hardware capability matrix，避免把硬件不支持误判为系统失败。
